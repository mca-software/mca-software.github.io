What it is

This is a debugger for Delphi applications, written in Delphi, built directly on the Windows Debug API. It plugs into Visual Studio Code through the Debug Adapter Protocol, so you get the editor's normal debugging experience — gutter breakpoints, the Variables and Watch panes, hover data tips, the call stack — against a Delphi executable that the Embarcadero IDE never has to open.

The repository ships three programs that share one engine:

ComponentWhat it does
Debug adapter The debugger itself, speaking DAP: breakpoints, stepping, call stacks, variables, expression evaluation. Any DAP client can drive it.
VS Code extension The client that makes it usable in the editor — the delphi-win64 debug type, the process picker for attaching, status-bar progress, and an editor for the exception rules.
MCP server The same engine exposed to an AI agent over the Model Context Protocol, so the agent can run a program and read its real state. See AI agents.

32-bit and 64-bit, one binary

The debugger is always a 64-bit process, whichever target it debugs. A 32-bit application is debugged across the WOW64 boundary, so the debugger never competes with the debuggee for a 32-bit address space — which matters on large projects, where symbol data is the memory hog: indexing a 523 MB .rsm from a real single-exe build peaks at 692 MB of working set. The target's PE header decides the machine model before the process starts; there is nothing to choose and no second adapter to install.

Installation

If you only want to use the debugger, do not build anything. Grab delphi-win64-debugger-setup-*.zip from the latest release, extract it anywhere and run Setup.exe. The debug adapter, the MCP server and the VS Code extension are already compiled inside it — no Delphi toolchain and no build step are needed on that machine.

Windows will warn that the executables are unsigned. Code signing certificates cost more per year than this project will ever make, which is nothing.

Compiler settings for the target

A debugger can only show what the compiler emitted. Compile the program you want to debug with full debug information, or most of this will not work. In the Delphi project options, for the Debug configuration of the platform you are building:

  • Compiling → Optimization off, Debug information on, Local symbols on
  • Linking → Debug information on, Include remote debug symbols on (this is the .rsm), Map file Detailed
  • Compiling → Use debug .dcus, if you want to step into the RTL and VCL rather than over them

On the command line that is:

dcc64 -$O- -V -VN -VR MyApp.dpr

Keep the .map and .rsm next to the .exe. What each artefact buys you:

ArtefactWithout it
TD32 section, .map, or JCL data — any oneNo source lines: no breakpoints, no stepping
.rsmBreakpoints and stepping still work, but local variables, types and expression evaluation are severely limited
Optimizations offBreakpoints land on the wrong line and locals read as garbage, because the code no longer matches the source
The same applies to every runtime package you want to step into: a BPL compiled without debug information stays a black box even when the host has full symbols.

Launch configuration

.vscode/launch.json in the project being debugged. The IDE plugin writes this for you; here is the minimum by hand: 

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug Delphi Win64",
      "type": "delphi-win64",
      "request": "launch",
      "program": "${workspaceFolder}/Win64/Debug/MyApp.exe",
      "mapFile": "${workspaceFolder}/Win64/Debug/MyApp.map",
      "sourceRoot": "${workspaceFolder}",
      "stopAtEntry": true
    }
  ]
}
PropertyDefaultDescription
programrequiredPath to the .exe to debug
mapFilesame path, .map extensionDelphi MAP file
sourceRootemptyRoot directory for source file lookup (searched one level deep)
stopAtEntryfalseBreak at the process entry point before any user code runs
exceptionRulesemptyPer-exception rule table — see Exception handling
useGlobalExceptionRulestrueAlso load the shared machine-wide rules file

To attach to a process that is already running, use "request": "attach" — the extension then shows a process picker. Attaching requires SeDebugPrivilege and auto-elevates when it can.

Your first session

  1. Compile your project with the settings above, so the .map and .rsm land next to the .exe.
  2. From the Delphi IDE, run Tools → Open in Visual Studio Code (the IDE plugin) — or open the folder in VS Code and write launch.json yourself.
  3. Set a breakpoint in the editor gutter, exactly as you would for any other language.
  4. Open Run and Debug (Ctrl+Shift+D), pick your configuration and press F5.
  5. Step with F10 (over), F11 (into), Shift+F11 (out); continue with F5.

Breakpoints are not limited to plain line stops:

  • Conditional breakpoints — a Pascal expression evaluated in the debuggee
  • Hit-count breakpoints and log points, which print instead of stopping
  • Data breakpoints (hardware watchpoints) via Break on Value Change / Break on Value Access in the Variables context menu — on a global, a unit variable or a local. The stop names the thread that wrote the cell and shows old -> new. There are four hardware slots, so the fifth request is refused by name rather than silently dropped; a watchpoint on a local is withdrawn the moment its frame exits, instead of quietly watching reused stack.
  • Address breakpoints from the Disassembly View gutter, which survive a runtime package unloading and reloading
  • Set next statement, to move execution without re-running

Inspecting state

Local variables come out of the reverse-engineered Delphi .rsm format, which is where most of the work went. What that gets you:

  • Objects, records and dynamic arrays expand in the Variables tree — all fields, all ancestor classes, nested
  • Generic collections: TList<T> and TDictionary<...> enumerate their elements
  • Parent-procedure locals are visible from inside nested procedures; anonymous-method parameters and closure-captured variables are inspectable (the captured $ActRec fields expand like a normal object)
  • Type-aware formatting for integers, floats, TDateTime, chars, strings, Variants, C-string pointers and dynamic arrays
  • Globals with decoded typeId, and a Registers scope
  • Per-thread inspection: selecting any thread shows that thread's own stack, with its frames' locals and watches readable

Expression evaluator

Watch, hover and the Debug Console share a full Pascal expression evaluator: qualified identifiers, arithmetic, comparison, boolean and set operators, string concatenation, indexing, type casts, is / as, Length / SizeOf / Ord / Low / High, enum and set literals, and method and property calls — executed in the debuggee, with raised exceptions aborted cleanly.

Writing back works too: setVariable handles primitives, floats, dates and chars, enums by name or ordinal, sets by bitmask at the correct storage width, strings through in-process @UStrAsg / @LStrAsg without leaking a reference, and writes through the pointer for var parameters.

When the symbols run out

A stop with no source — OS code, a module built without debug information, an address the debug info does not cover — opens a real document instead of going silent: the address, module and reason, the disassembly around the stop with the current instruction marked, and the source file and line per instruction wherever the line table has one. The Disassembly View decodes real x86/x64 (Zydis) with symbolication, and shows undecodable bytes honestly as db XX rather than guessing.

When the unwinder cannot get through code built without frame pointers, an opt-in raw stack scan — toggled from the Call Stack title bar — sweeps the thread's stack for your own routines, resolved against every loaded module and marked [raw] / [raw?] so they are never mistaken for real callers.

Exception handling

The BREAKPOINTS view exposes four exception filters — delphi, av, all, unhandled — each with an optional per-class condition. On a stop you get the exception class name and message, and the live exception object is inspectable as the $exception pseudo-variable in Locals and Watch.

Beyond the filters there is a rule engine. Rules match on class, message, regex, unit or line, and act with ignore, log, logStack or break — which is how you survive a codebase that raises handled exceptions in a loop: 

"exceptionRules": [
  { "match": { "class": "EFileNotFound" }, "action": "ignore" },
  { "match": { "class": "EDatabaseError", "message": "deadlock" },
    "action": "logStack" },
  { "match": { "unit": "MyRiskyUnit" }, "action": "break" }
]

Rules can live in the project's launch.json or in a shared machine-wide file (%USERPROFILE%\.DelphiWinDebugger\exceptionRules.json) applied across projects, and can be edited from a UI in the extension rather than by hand.

Debugging from an AI agent (MCP)

The same engine is exposed over the Model Context Protocol, so an agent can debug a Delphi program the way a developer does — run it, stop it, and read the real state — instead of inferring behaviour from the source. In practice this is the difference between an agent that guesses why a value is wrong and one that sets a breakpoint and looks.

Install.exe offers to register the server at the end of an install; from a source checkout it is one script: 

cmd /c build_mcp.bat
powershell -ExecutionPolicy Bypass -File register-mcp.ps1 ^
  MCPDebugger\Win64\Debug\DelphiDebuggerMcp.exe

That registers the server as delphi-win64-debugger with Claude Code (user scope) and with VS Code by merging the user mcp.json. It is idempotent, and -Unregister removes it.

Two of them matter more than the rest. launch_from_config and attach_from_config read the launch.json the IDE plugin generated, so an agent starts a session with the project's real symbol and source paths rather than a hand-built approximation. get_compact_debug_snapshot returns location, stack and locals in one call — usually what an agent wants after a stop, at a fraction of the tokens three round trips would cost.

Known limitations

  • Child processes are not tracked — the debugger launches with DEBUG_ONLY_THIS_PROCESS
  • On a 32-bit target, locals are unavailable in optimised (-$O+) builds
  • Source files are resolved by searching sourceRoot and one level of subdirectories; if a file name appears twice, the first match wins
  • The shipped executables are unsigned, so SmartScreen will complain on first run
